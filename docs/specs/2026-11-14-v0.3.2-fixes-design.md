# 0.3.2 fixes: design

Status: draft for review · Date: 2026-11-14 · Builds on:
`docs/specs/2026-10-26-phase-3-remote-design.md`

## Why

A review of the whole project after three weeks of running (2026-11-13/14) found nothing broken,
but several things that will mislead users or the owner when a source changes or a restaurant
closes, the most pressing being Yolo during the Christmas break. 0.3.2 fixes those, plus the open
minor findings of the phase 3 review that are worth fixing. No new features.

Non-goals: new tools, new restaurants, changing the history format (`stats.json` stays schema 1),
evicting `day:*` cache entries (about 250 a year; Worker instances restart often).

## Fixes

1. **Yolo with no menu days (owner chose approach A).** Today a page with no dated day headings
   is a non-retryable source error, so a closed Yolo (Christmas) would be recorded as "not
   collected" every day, fail the 10:30 collection and email the owner daily, and users would be
   told the site may have changed.
   - If the page has a menu section (`.pricing__section--type-menu`) but no dated headings, Yolo
     has published nothing: return `{ days: {}, coverage: null }`, as LUT Buffet does between
     seasons. Today then reads "not published yet", the collector records "nothing listed", and
     nothing fails.
   - If there is no menu section at all, it stays a source error (a redesign must still show up).
   - Approaches considered: B (any empty page means closed: hides a redesign) and C (keep the
     error, stop the emails: users still misinformed). A is a guess about a page never seen; check
     the real page at the first closure.

2. **Poweresta menu list shape.** `pickSlugs` returns `[]` for any unexpected response, which
   reads as "nothing published". A valid list (even empty) keeps today's behaviour; anything that
   is not a list of objects becomes `SourceError('Poweresta: unexpected menus response', false)`,
   shown as a source error.

3. **Empty allergen list is unknown.** `powerestaAllergens([])` counts all 14 allergens as assessed
   and absent. An empty list now means "no list" (nothing assessed), like a missing one: unknown is
   never safe. No live or captured data has an empty list, so no answer changes today.

4. **Smoke test checks the version.** `smoke:remote` also fails unless the server reports this
   checkout's `VERSION`, so the deploy workflow's retries wait for the new deployment instead of
   passing on the old one.

5. **Rate-limit binding failure.** If the Workers rate-limit binding throws, the request is
   treated as allowed by the binding (logged) and the per-instance counter still applies; today the
   exception escapes as a bare HTTP 500.

6. **`stats.json` validation.** `decodeStatsIndex` also rejects (malformed) dates that aren't valid
   `YYYY-MM-DD`, days that aren't strictly ascending, `firstDate`/`lastDate` that don't match the
   days, and duplicate restaurant ids. `monthsInRange` returns `[]` for invalid input instead of
   looping forever.

7. **Forward compatibility of `stats.json`.** A restaurant id or diet tag this version doesn't know
   is skipped instead of making the whole file malformed, so older installs keep working (minus the
   new restaurant or label) when one is added. Unknown status kinds remain malformed.

8. **Deploy only `main` and tags.** The deploy job runs only for `refs/tags/v*` or `refs/heads/main`,
   so a manual run can't deploy another branch.

9. **Dependencies.** Update within the existing version ranges (MCP SDK 1.32.2, wrangler,
   vitest, eslint, prettier, typescript-eslint, @cfworker/json-schema) and refresh the lockfile so
   `npm audit` is clean. The flagged `hono` code is only used by the SDK's Node HTTP server, which
   this project doesn't run, so this is hygiene, not an exploitable issue. No major upgrades
   (TypeScript 7, @types/node 26).

10. **Docs.** README limitations give the measured CPU (warm 1–4 ms, fresh instances up to about
    20–27 ms, all served) instead of "slightly more than 10 ms". ChatGPT steps corrected if the
    owner's working steps differ. CHANGELOG 0.3.2.

## Testing

Each code fix starts with a failing test (1–7), using a synthetic closed-Yolo page for 1. 8–10
are config and docs, checked by CI and by reading. Full suite in UTC and Europe/Helsinki,
`worker:check`, then the usual release: merge, tag (deploys and now version-checks), npm, GitHub
release.
