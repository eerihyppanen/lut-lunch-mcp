# LUT Lunch MCP — Phase 2 (Menu History) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record every restaurant's menu daily with GitHub Actions, and let the server answer past-day, "how often", "when last" and trend questions from that shared history (release 0.2.0).

**Architecture:** Pure history functions in `src/core/history/` turn `RestaurantDay[]` into day files and a combined dataset. `scripts/collect.ts` (Node, run by `collect.yml`) writes them to the `data` branch. The server loads `history.json` lazily through a `fetch`-only `RemoteHistoryStore`. `LiveMenuService` serves past dates from it, and a new `menu_stats` tool computes statistics with a pure `src/mcp/stats.ts`.

**Tech Stack:** As in phase 1 (Node ≥ 22, TypeScript 6.0, MCP SDK 1.32, zod 4, Vitest 5). The collector uses `node:fs` and runs through `tsx`.

**Spec:** `docs/specs/2026-10-24-phase-2-history-design.md` (§n below). The phase 1 spec and plan still apply where this plan doesn't change them.

## Global Constraints

- `src/core/**` uses only `fetch` and standard JavaScript (the lint guard enforces it). File access lives in `scripts/collect.ts` only.
- Stored data (day files, `history.json`) uses the core's camelCase types. Tool output stays snake_case.
- Both files carry `"schema": 1`. Any other schema value → `SourceError('History data uses schema <n>; update lut-lunch-mcp.', false)`.
- Default history URL: `https://raw.githubusercontent.com/eerihyppanen/lut-lunch-mcp/data/history.json`. `LUT_LUNCH_HISTORY_URL` overrides it, read in `src/bin/stdio.ts` only.
- History cache key: `'history'`, fresh for `6 * 3600_000` ms, through the existing `CachedLoader`.
- Day file path: `<dataDir>/days/YYYY/MM/YYYY-MM-DD.json`. Combined file: `<dataDir>/history.json`.
- Day files: 2-space JSON plus a trailing newline. `history.json`: compact JSON plus a trailing newline.
- Merge rank: `open` (3) > `no_menu` (2) > `error` (1). A tie keeps the existing entry.
- Cron: `30 6 * * *` and `30 10 * * *`. The 10:30 run and `workflow_dispatch` pass `--fail-on-error`.
- Tool descriptions are the exact text in spec §6.4 (`get_menu`, `find_dishes`) and §7 (`menu_stats`).
- Errors from `menu_stats` when history can't load: `Menu history is temporarily unavailable; try again later.` (retryable source error), or the schema message (non-retryable).
- Release: version `0.2.0` via `npm version minor`.
- Commits go through the usual gate: format, lint, typecheck, `TZ=UTC` tests and build must all pass.

## Review Focus

1. **A past date before history starts** (e.g. `2025-05-05`, or a day before the first collection) must answer `no_menu / history_not_available`, not an error. Test added to Task 4.
2. **`menu_stats` with `to` in the future or `from` after `to`.** Future days are simply not recorded (no error); `from` after `to` is an input error. Test added to Task 6.
3. **A malformed or newer-schema `history.json`.** `menu_stats` gives a clear non-retryable error, and today's menus still work. Tests added to Tasks 3 and 6.
4. **The collector runs again on an already complete day.** It must not rewrite the files, so the workflow makes no commit. Test added to Task 2.
5. **Case and diacritics in a `menu_stats` query** (`"LOHI"`, `"Lohi"`) give the same counts as `"lohi"`. Test added to Task 5.

### Task 2: Collector script

**Files:**
- Create: `scripts/collect.ts`, `test/scripts/collect.test.ts`
- Modify: `package.json` (script `"collect": "tsx scripts/collect.ts"`)

**Interfaces:**
- Consumes: `toHistoryDay`, `mergeHistoryDay`, `buildHistoryDataset`, `HistoryDaySchema` (Task 1); `createLiveMenuService`, `createFetchHttpClient`, `USER_AGENT`, `helsinkiToday`, `VERSION`.
- Produces: `runCollect(opts: { dataDir: string; date: string; failOnError: boolean; service: MenuService; now: () => Date; log: (line: string) => void }): Promise<{ exitCode: 0 | 1; wroteDay: boolean; wroteHistory: boolean }>`
- CLI (only when run directly, i.e. `import.meta.url === pathToFileURL(process.argv[1]).href`): parses `--data-dir` (default `data`), `--date` (default `helsinkiToday(new Date())`) and `--fail-on-error`. It builds the live service, calls `runCollect`, and calls `process.exit(exitCode)`.

`runCollect` steps (spec §5.1):
1. `service.getDays([date], [...RESTAURANT_IDS])`, then `toHistoryDay(date, rows, now().toISOString(), VERSION)`.
2. Read and validate the existing day file if present, then merge.
3. Write the day file only if `changed`.
4. Rebuild the dataset from every `days/**/*.json`.
5. Write `history.json` only if its content minus `generatedAt` differs from the file on disk.
6. Log one line per restaurant: `<id>: <kind>[ <reason>]`.
7. `exitCode` = 1 iff `failOnError` and any merged restaurant is `error`.
